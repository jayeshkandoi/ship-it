STAGE 5 · DEEP LEARNING

Portfolio and capstone

Turn a real problem into a complete, deployed project that demonstrates engineering judgment.

How to use this stage: read one lesson, reproduce the example without copying, explain the diagram aloud, then complete the exercise. Open the answer only after making an attempt.

LESSON 1 · 30–45 min

Choose a real problem and scope the MVP

A portfolio project is strongest when it solves a clear problem for a defined user. A feature list is not a product plan: first understand the workflow, constraints and success criteria.

Problem statement

Write: [user] needs [job] because [pain]. Avoid starting with a technology choice. Interview two or three likely users or observe the workflow. Separate what users say they want from the problem they are trying to solve.

MVP and non-goals

The minimum viable product is the smallest complete workflow that tests the core value. List must-have behavior, later ideas and explicit non-goals. A small deployed product with thoughtful error states is more impressive than a large unfinished feature list.

  • Define one primary user and one primary workflow.
  • Write acceptance criteria that can be tested.
  • Identify data that must be stored and who may access it.
  • Set a time budget and cut scope before cutting testing.

Example scope

undefined

Project: shared task board
MVP: create board → invite member → add task → complete task
Non-goals: chat, file uploads, billing, mobile app
Success: a new user completes the workflow in < 3 minutes
Risks: access control, duplicate invitations, data loss
Practice task: Write a one-page product brief for a problem you understand. Include target user, pain, proposed workflow, MVP, non-goals, success metric and top three risks.
Check your understanding

Question: Why explicitly list non-goals?

Answer: They protect the project from scope creep and make trade-offs visible.

Why: A bounded project can be completed, tested and explained.

Interview practice

Question: How do you decide what belongs in an MVP?

Strong answer should mention: Choose the smallest end-to-end workflow that tests the core user value; defer features that do not validate that assumption.

LESSON 2 · 30–45 min

Architecture and system design

Architecture is the set of important boundaries and decisions in a system. Start with requirements and data flow, then choose the simplest design that meets them. Explain why you chose it and what would make you change it.

Functional and non-functional requirements

Functional requirements describe what users can do. Non-functional requirements describe qualities such as latency, availability, security, accessibility, maintainability and cost. Quantify where possible: expected users, request volume, data size and acceptable response time.

Data model before endpoints

List entities, relationships, ownership and lifecycle. Decide which fields are required, unique or sensitive. Design authorization around ownership and membership; do not rely on hiding buttons in the frontend. Every server operation must enforce access.

Trade-offs and evolution

A monolith is often the best starting point: one deployable application with clear internal modules. Split services only when independent scaling, ownership or deployment needs justify the operational cost. Document alternatives considered and why the chosen option fits current scale.

Practice task: Create a context diagram, data model, three API contracts and a short architecture decision record. Include one alternative you rejected and the reason.
Check your understanding

Question: Why start with a monolith for many portfolio projects?

Answer: It is simpler to build, test, deploy and operate while still allowing clear internal boundaries.

Why: Premature distributed architecture adds network, deployment and consistency problems before there is evidence they are needed.

Interview practice

Question: How would you explain an architecture decision in an interview?

Strong answer should mention: State constraints, options, trade-offs, chosen approach, risks and what new evidence would cause you to revisit it.

LESSON 3 · 30–45 min

Build quality: Git, code review and security

Professional quality is visible in the way changes are made, not only in the final screenshot. Small commits, readable code, automated checks and security basics make a project easier to trust.

A healthy Git workflow

Use a branch for a focused change. Commit related changes together with a message describing intent. Keep the pull request small enough to review. Describe what changed, why, how to test it and any risk. Do not commit .env files, build output or credentials.

Code review checklist

undefined

  • Does the change meet the acceptance criteria?
  • Are names and boundaries understandable?
  • Are errors and empty states handled?
  • Are tests added for changed behavior?
  • Are authorization and input validation enforced server-side?
  • Does it affect performance, accessibility or data migration?

Security basics

Validate input on the server, parameterize SQL, encode output in the correct context, use HTTPS, store passwords with a modern password hashing algorithm, protect sessions, apply authorization on every sensitive operation, and keep dependencies updated. Use least privilege for database and deployment credentials.

Readable code

Prefer small functions with clear names and explicit inputs/outputs. Avoid hidden global state and duplicated business rules. Comments should explain why a non-obvious decision exists, not restate what the next line does.

Practice task: Open a pull request for one feature in your project. Use the checklist to review your own change, add tests for a bug-prone edge case, and record one refactor you intentionally deferred.
Check your understanding

Question: Why is frontend-only authorization unsafe?

Answer: Users can bypass or modify client-side code and send requests directly; the server must enforce permissions.

Why: The client is controlled by the user and cannot be a security boundary.

Interview practice

Question: What do you look for in code review?

Strong answer should mention: Correctness, maintainability, test coverage, edge cases, security, performance and whether the change solves the stated problem.

LESSON 4 · 30–45 min

Testing, deployment and operations

A project is not complete when it works on your laptop. It is complete when another person can run it, use it, and recover when something goes wrong.

Test strategy

Map tests to risks. Test business rules with unit tests, persistence and API boundaries with integration tests, and one or two critical user journeys end to end. Include invalid input, permission failures, empty data and network failures.

Deployment checklist

undefined

  • Production environment variables are configured outside source control.
  • Database migrations are repeatable and backed up.
  • HTTPS and secure cookie settings are enabled.
  • Health checks and structured logs work.
  • A rollback or recovery procedure is documented.
  • A smoke test verifies the deployed critical workflow.

Release and monitor

Deploy a known build artifact. Prefer a staged rollout when possible. Watch error rate, latency and resource use after release. If the release causes harm, roll back first and investigate after service is stable. Keep a changelog for meaningful releases.

README that earns trust

A good README includes the problem, screenshots or short demo, features, architecture diagram, technology choices, prerequisites, setup commands, environment variable names (not values), migrations, tests, deployment link and known limitations.

Practice task: Deploy your MVP publicly. Ask a person unfamiliar with the code to follow the README on a clean machine. Fix every unclear setup step and capture a short demo.
Check your understanding

Question: What should a README include beyond a feature list?

Answer: Setup instructions, configuration, architecture, tests, deployment, screenshots/demo and known limitations.

Why: A reviewer needs to verify the project, not merely read that it exists.

Interview practice

Question: How do you respond when a deployment breaks production?

Strong answer should mention: Mitigate impact quickly, roll back or disable the faulty change, communicate status, preserve evidence, then investigate and add prevention.

Stage project

Turn a real problem into a complete, deployed project that demonstrates engineering judgment.

  1. Write a one-page scope and define the user problem.
  2. Build the smallest working version before adding extras.
  3. Test the happy path, invalid input, empty state and failure path.
  4. Write a README with setup steps, screenshots and trade-offs.
  5. Ask someone to use it and record what confused them.

Definition of done: a stranger can run it, understand its purpose, and verify its main behavior.
