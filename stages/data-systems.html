Data and systems

Learn how applications store data, handle load, run in containers and stay reliable in production.

LESSON 1 · 30–45 min

Relational databases and SQL fundamentals

A relational database stores data in tables with defined relationships. SQL describes the data you want, while the database engine chooses an execution plan. A sound schema reduces duplication and protects data integrity.

Tables, keys and relationships

A row represents one entity instance; a column represents an attribute. A primary key uniquely identifies a row. A foreign key references a key in another table and enforces a relationship. Use constraints such as NOT NULL, UNIQUE and CHECK so invalid data is rejected close to where it is stored.

CREATE TABLE customers (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email TEXT NOT NULL UNIQUE,
  name TEXT NOT NULL
);

CREATE TABLE orders (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers(id),
  total_cents INTEGER NOT NULL CHECK (total_cents >= 0),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CRUD and filtering

SELECT reads, INSERT creates, UPDATE changes and DELETE removes. Be explicit about columns. Parameterize values in application code; never build SQL by concatenating untrusted user input.

SELECT id, email
FROM customers
WHERE email ILIKE $1
ORDER BY id DESC
LIMIT 20;

UPDATE orders
SET total_cents = $1
WHERE id = $2;

Joins and aggregation

INNER JOIN keeps rows with matches on both sides. LEFT JOIN keeps every left-side row and fills missing right-side columns with NULL. GROUP BY forms groups for aggregate functions such as COUNT, SUM and AVG. WHERE filters rows before grouping; HAVING filters groups afterward.

SELECT c.id, c.name, COUNT(o.id) AS order_count
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name
HAVING COUNT(o.id) >= 2
ORDER BY order_count DESC;

Normalization

Normalization separates facts into tables so the same fact is not copied into many rows. First normal form uses atomic values; second and third normal forms remove partial and transitive dependencies. Denormalization can be useful for measured performance needs, but introduces consistency work.

Practice task: Design a schema for users, projects and project memberships. Add primary/foreign keys, uniqueness constraints and a query that lists each project with its member count.
Check your understanding

Question: Why use a foreign key instead of trusting application code?

Answer: The database enforces referential integrity for every writer, including scripts and concurrent requests.

Why: Rules enforced only in one application path can be bypassed by another writer.

Interview practice

Question: Explain INNER JOIN vs LEFT JOIN.

Strong answer should mention: INNER JOIN returns matching rows only; LEFT JOIN retains every left row and returns NULLs for missing right-side matches.

LESSON 2 · 30–45 min

Indexes, query plans and transactions

Indexes trade storage and write overhead for faster reads. Query planning chooses scans and join strategies based on statistics and available indexes. Transactions group operations into one logical unit.

How indexes work

A B-tree index keeps keys ordered and is useful for equality and range lookups. A composite index is ordered by its leading columns, so column order matters. An index on (customer_id, created_at) can support filtering by customer and often ordering by date; it may not efficiently support filtering only by created_at.

CREATE INDEX orders_customer_created_idx
ON orders (customer_id, created_at DESC);

EXPLAIN ANALYZE
SELECT id, total_cents
FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 20;

Read the query plan

EXPLAIN shows the planner's strategy; EXPLAIN ANALYZE runs the query and reports actual timings and row counts. Compare estimated and actual rows. Large mismatches can point to stale statistics or skewed data. A sequential scan is not automatically bad; for small tables or queries returning much of a table it can be faster.

ACID transactions

Atomicity means all operations happen or none do. Consistency means constraints remain satisfied. Isolation controls what concurrent transactions can observe. Durability means committed data survives failures. Use transactions when multiple writes must succeed together.

BEGIN;
UPDATE accounts
SET balance = balance - 500
WHERE id = 1;

UPDATE accounts
SET balance = balance + 500
WHERE id = 2;
COMMIT;

Isolation and concurrency

Concurrent transactions can cause lost updates, non-repeatable reads or phantom rows depending on isolation level. Use row locks or optimistic version checks for contested updates. Keep transactions short and access rows in a consistent order to reduce deadlocks.

Transaction A                 Transaction B
BEGIN                         BEGIN
read balance = 100
                              read balance = 100
write 80
                              write 70  ← stale value risk
COMMIT                        COMMIT
Use locking / version checks to coordinate writes
Practice task: Use EXPLAIN ANALYZE to compare a query before and after adding a suitable index. Record execution plan, row estimates, timing and the write/storage trade-off.
Check your understanding

Question: Why might a composite index (a,b) not help a query filtering only on b?

Answer: B-tree ordering starts with a, so the index is not generally ordered by b alone.

Why: The leftmost-prefix principle makes the order of composite index columns important.

Interview practice

Question: What is a database transaction and when do you need one?

Strong answer should mention: A transaction makes a set of operations behave atomically; use it when related writes must succeed or fail together, such as transferring money.

LESSON 3 · 30–45 min

Caching, queues and background jobs

Databases are the source of truth for many applications, but repeated expensive reads and long-running work can strain request latency. Caches and queues help when their consistency and failure behavior are designed deliberately.

Cache-aside pattern

The application checks a cache first. On a miss it reads the database, stores the result with a time-to-live, and returns it. On writes, invalidate or update the cache. Cache keys must include every input that changes the result, including user or permission context when relevant.

Request → Cache lookup
            ├─ hit  → return cached value
            └─ miss → Database read → set TTL → return
Write → Database commit → invalidate related cache keys

Cache trade-offs

A cache can serve stale data, consume memory and create invalidation bugs. Use short TTLs for data that changes frequently. Avoid caching sensitive user data in shared keys. Add request coalescing or a short-lived lock to reduce cache stampedes when a popular key expires.

Message queues

A producer sends a message; a broker stores it; a consumer processes it. Queues decouple request handling from slow work such as sending email, generating reports or processing images. Design for at-least-once delivery: a message may be delivered more than once, so consumers should be idempotent.

// Conceptual job payload
{
  "id": "job-8f2",
  "type": "send_receipt",
  "orderId": 42,
  "attempt": 1
}

Retries, dead letters and the outbox

Retry transient failures with exponential backoff and jitter. Do not retry permanent validation errors forever. After a limit, move failed messages to a dead-letter queue for inspection. The transactional outbox pattern writes the business change and an event record in one database transaction; a worker publishes the event later.

Practice task: Add a background email job to an application. Make processing idempotent, retry temporary provider failures with backoff, and record permanently failed jobs for review.
Check your understanding

Question: Why should a queue consumer be idempotent?

Answer: Because at-least-once delivery can run the same message more than once; idempotency prevents duplicate side effects.

Why: Distributed systems can fail after work succeeds but before the acknowledgement reaches the broker.

Interview practice

Question: What is cache invalidation?

Strong answer should mention: It is deciding when cached data becomes stale and ensuring subsequent reads do not keep returning obsolete values; discuss TTL, write-through or explicit invalidation and consistency needs.

LESSON 4 · 30–45 min

Docker, containers and deployment

A container packages an application with its runtime dependencies while sharing the host kernel. Images are immutable templates; containers are running instances. Containers improve repeatability but do not automatically make an application secure or highly available.

Image and container lifecycle

A Dockerfile describes image layers. Build an image, run a container from it, expose the required port and pass configuration through environment variables. Keep secrets out of the image and source repository.

FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
ENV NODE_ENV=production
EXPOSE 3000
CMD ["node", "server.js"]

Compose for local development

Docker Compose defines services, networks and volumes in one file. Use a named volume for local database persistence. A container's filesystem is disposable; do not rely on it as the only copy of important data.

services:
  app:
    build: .
    ports: ["3000:3000"]
    environment:
      DATABASE_URL: postgres://app:dev@db:5432/app
    depends_on:
      - db
  db:
    image: postgres:16
    volumes:
      - pgdata:/var/lib/postgresql/data
volumes:
  pgdata:

Configuration and health

Separate configuration from code. Validate required environment variables at startup. Provide a health endpoint that checks whether the process can serve traffic; use a separate readiness check when dependencies must be available before receiving requests. Log to stdout/stderr so the platform can collect logs.

Practice task: Containerize a small API and Postgres database with Compose. Document how to start, stop, inspect logs, persist data and run tests in a clean environment.
Check your understanding

Question: Why should secrets not be copied into a Docker image?

Answer: Image layers can be inspected and shared; secrets may remain in layer history even if later deleted.

Why: Inject secrets at runtime through a secret manager or protected deployment configuration.

Interview practice

Question: What is the difference between an image and a container?

Strong answer should mention: An image is the built, immutable template; a container is a running instance created from that image.

LESSON 5 · 30–45 min

Testing, CI/CD and observability

Testing provides fast feedback and protects behavior as code changes. CI automates checks on every change; CD automates delivery. Observability helps explain what a running system is doing.

Testing pyramid

Unit tests verify small functions quickly. Integration tests verify boundaries such as database queries and HTTP handlers. End-to-end tests exercise critical user journeys through the real application stack. Favor many focused tests and a smaller number of high-value end-to-end tests.

          /\
         /E2E\       few, slower, broad
        /------\
       /Integr. \    service + database boundaries
      /----------\
     /   Unit     \  many, fast, focused
    /______________\

Arrange, Act, Assert

A readable test has setup, one action and clear expectations. Test normal behavior, boundaries, invalid input and failure behavior. Avoid tests that only repeat implementation details; assert externally visible behavior.

test("rejects an empty title", async () => {
  const response = await request(app)
    .post("/api/tasks")
    .send({ title: "   " });

  expect(response.status).toBe(400);
  expect(response.body.error).toBe("Title is required");
});

Continuous integration

A CI pipeline typically checks formatting, lint, unit/integration tests and build output. Make failures visible and reproducible. Pin dependency versions, cache package downloads safely, and protect deployment credentials. Keep the pipeline fast enough that developers do not ignore it.

Logs, metrics and traces

Logs describe individual events and should include a request or trace ID. Metrics summarize behavior over time: request rate, error rate, latency and saturation are useful starting signals. Traces connect spans across services to show where time was spent. Do not log passwords, tokens or unnecessary personal data.

SLOs and incident learning

A service-level indicator is a measured signal such as successful request ratio or p95 latency. A service-level objective is the target. An error budget makes reliability trade-offs explicit. After an incident, write a blameless review: impact, timeline, contributing factors, detection gaps and concrete follow-up actions.

Practice task: Create a CI workflow that installs dependencies, runs lint and tests, and builds the app. Add structured request logs and a health endpoint. Write a short incident runbook for a failed deployment.
Check your understanding

Question: What does p95 latency mean?

Answer: 95% of measured requests completed at or below that latency; the slowest 5% took longer.

Why: Percentiles expose tail latency that an average can hide.

Interview practice

Question: How would you investigate a sudden increase in API errors?

Strong answer should mention: Check dashboards for rate, status codes and latency; correlate logs/traces by request ID; identify recent deploys/dependency failures; mitigate safely; then document root cause and prevention.
