STAGE 3 · DEEP LEARNING

Web and backend

Learn how browser interfaces, APIs and servers fit together. These lessons move from semantic HTML to a tested backend service.

How to use this stage: read one lesson, reproduce the example without copying, explain the diagram aloud, then complete the exercise. Open the answer only after making an attempt.

LESSON 1 · 30–45 min

HTML: semantic structure and accessibility

HTML describes meaning and structure. Browsers build a document tree from elements; CSS controls presentation and JavaScript adds behavior. Good markup makes pages understandable to assistive technology, search engines and future developers.

Elements, attributes and the DOM

An element usually has an opening tag, content and a closing tag. Attributes add configuration such as href, src, alt, type and aria-label. The browser parses markup into a Document Object Model (DOM), a tree that scripts can inspect and update. Use headings in a meaningful hierarchy rather than choosing a heading because of its default size.

Semantic landmarks

Use header, nav, main, section, article, aside and footer according to their meaning. A button performs an action; an anchor navigates. A clickable div does neither accessibly by default. Inputs need associated labels. Images that convey information need useful alt text; decorative images should use an empty alt attribute.

  • One main landmark per page is a useful default.
  • Use a real button for actions and an anchor for navigation.
  • Keep visible keyboard focus; do not remove outlines without a replacement.
  • Use table headers for tabular data, not for page layout.

Check your understanding

Question: Why is a button preferable to a clickable div for submitting a form?

Answer: A button has built-in keyboard behavior, focusability and semantics, and works naturally with forms.

Why: Native HTML controls provide behavior that otherwise must be recreated and tested.

Interview practice

Question: How would you make a form accessible?

Strong answer should mention: Semantic form elements, explicit labels, correct input types, required/error messaging, keyboard access, focus management and useful status announcements.

LESSON 2 · 30–45 min

CSS: layout, responsive design and maintainability

CSS maps a set of selectors and declarations onto the DOM. The cascade resolves competing declarations using origin, importance, specificity and source order. Layout is easier when you understand the box model and choose a layout system deliberately.

The box model

Every element has content, padding, border and margin. With content-box, declared width applies to content only. With border-box, width includes padding and border. A common project-wide rule is box-sizing: border-box so sizing is predictable.

*, *::before, *::after {
  box-sizing: border-box;
}
.card {
  width: min(100%, 42rem);
  padding: 1.25rem;
  border: 1px solid #888;
}

Flexbox vs Grid

Flexbox is ideal for arranging items along one axis, such as a toolbar or navigation row. Grid is ideal for two-dimensional layouts, such as a card gallery with rows and columns. Neither is a replacement for the other.

Flexbox:  [logo] [nav] [button]  → one axis
Grid:      [card] [card] [card]
           [card] [card] [card]  → rows + columns

Responsive thinking

Start with content constraints, not device names. Use flexible widths, minmax(), wrapping and media queries only when the layout needs a change. Test long text, zoom, touch targets and narrow screens.

.cards {
  display: grid;
  grid-template-columns: repeat(
    auto-fit, minmax(min(100%, 16rem), 1fr)
  );
  gap: 1rem;
}
img { max-width: 100%; height: auto; }

Debug the cascade

When a style does not apply, inspect the element in DevTools. Check whether the selector matches, whether a later or more specific declaration wins, whether the property is inherited, and whether a parent layout constrains the element. Avoid solving every conflict with !important.

Practice task: Build a responsive three-card project gallery. At 320px wide it should have no horizontal overflow; at desktop it should use multiple columns. Add visible focus states.
Check your understanding

Question: When would you choose Grid over Flexbox?

Answer: Choose Grid when you need to control rows and columns together; choose Flexbox for a primarily one-dimensional arrangement.

Why: Picking the layout model that matches the problem reduces unnecessary CSS and fragile spacing hacks.

Interview practice

Question: How do you debug a layout that overflows on mobile?

Strong answer should mention: Inspect the overflowing element, check fixed widths and min-width, long unbreakable content, images, grid tracks and viewport assumptions; reproduce at narrow widths and fix the source.

LESSON 3 · 30–45 min

JavaScript in the browser: events, async and state

Browser JavaScript responds to events, changes the DOM and communicates with servers. The event loop lets JavaScript coordinate asynchronous work without blocking the page while network or timer operations are pending.

Scope and data

Use const by default and let when reassignment is required. Prefer strict equality (===). Objects and arrays are reference values: assigning one variable to another does not clone the object. Keep state changes explicit and avoid mutating shared objects unexpectedly.

const user = { name: "Asha", active: true };
const copy = { ...user }; // shallow copy
copy.active = false;
console.log(user.active); // true

Events and event delegation

An event travels through capture, target and bubble phases. Delegation attaches one listener to a stable parent and checks which child initiated the event. It is useful for lists whose items are created dynamically.

document.querySelector("#list").addEventListener("click", event => {
  const button = event.target.closest("button[data-id]");
  if (!button) return;
  removeItem(button.dataset.id);
});

Promises and async/await

A Promise represents a value that may arrive later. await pauses the current async function until the promise settles; it does not freeze the browser. Always handle failures and check HTTP response status because fetch resolves even for many 4xx and 5xx responses.

async function loadProfile(id) {
  const response = await fetch(`/api/users/${id}`);
  if (!response.ok) {
    throw new Error(`Request failed: ${response.status}`);
  }
  return response.json();
}

loadProfile(42)
  .then(showProfile)
  .catch(showError);

The event loop

Promise callbacks run as microtasks. Timers and many event callbacks are tasks. Long synchronous loops block rendering and input; split expensive work or move suitable computation to a Web Worker.

Call stack: run current synchronous code
      ↓
Browser APIs: network, timers, events
      ↓ when ready
Task / microtask queues
      ↓
Event loop schedules the next callback
      ↓
Browser can render between tasks
Practice task: Build a searchable list with add, complete and delete actions. Persist it in localStorage, show an empty state, and handle malformed stored JSON safely.
Check your understanding

Question: Why should fetch code check response.ok?

Answer: Because fetch normally resolves for HTTP errors such as 404 and 500; response.ok is false for non-success status codes.

Why: Network failure and an HTTP error are different failure modes and both need deliberate handling.

Interview practice

Question: Explain the event loop to a teammate.

Strong answer should mention: Synchronous code runs on the call stack; browser APIs complete asynchronous work; callbacks are queued and scheduled when the stack is clear, with microtasks drained before the next task.

LESSON 4 · 30–45 min

React: components, state and effects

React builds user interfaces from components. A component receives props and returns a description of UI. State represents data that changes over time; when state changes, React renders the component again.

Components and props

Keep components focused and compose them. Props flow from parent to child and should be treated as read-only. Give list items stable keys so React can match items between renders.

function TaskRow({ task, onToggle }) {
  return (
    <li>
      <button onClick={() => onToggle(task.id)}>
        {task.done ? "Undo" : "Complete"}
      </button>
      {task.title}
    </li>
  );
}

State is a snapshot

Use useState for local state. State updates schedule a render; they do not mutate the value in the current render. When the next value depends on the previous value, use the updater form. Avoid storing values that can be calculated from existing state.

const [count, setCount] = useState(0);
function addTwo() {
  setCount(current => current + 2);
}

Effects and data fetching

useEffect synchronizes a component with an external system. It is not a general place to calculate derived values. Include every reactive value used by the effect in its dependency list, clean up subscriptions, and guard against stale requests when appropriate.

useEffect(() => {
  const controller = new AbortController();
  fetch("/api/tasks", { signal: controller.signal })
    .then(r => {
      if (!r.ok) throw new Error("Could not load tasks");
      return r.json();
    })
    .then(setTasks)
    .catch(error => {
      if (error.name !== "AbortError") setError(error.message);
    });
  return () => controller.abort();
}, []);

Check your understanding

Question: Why should a list use stable keys instead of array indexes?

Answer: Stable keys let React identify the same logical item after insertions, deletions or reordering.

Why: Index keys can associate component state with the wrong item when list order changes.

Interview practice

Question: When should you use useEffect?

Strong answer should mention: For synchronization with external systems such as subscriptions, browser APIs or network requests—not for values that can be derived during render.

LESSON 5 · 30–45 min

HTTP APIs, Node.js and backend foundations

A backend receives requests, validates them, enforces business rules, reads or writes data, and returns a response. An API is a contract: clients depend on its routes, methods, status codes and data shapes.

REST resource design

Model endpoints around resources. GET reads, POST creates or triggers a non-idempotent operation, PUT replaces, PATCH partially updates and DELETE removes. Use plural nouns and predictable response shapes. Validate input on the server even if the browser already validates it.

GET    /api/tasks
GET    /api/tasks/42
POST   /api/tasks
PATCH  /api/tasks/42
DELETE /api/tasks/42

// POST body
{ "title": "Write tests" }

A minimal Express route

Routes should parse input, validate it, call a service or data layer, and return an intentional status. In larger applications keep routing, business logic and persistence separate.

app.post("/api/tasks", async (req, res, next) => {
  try {
    const title = String(req.body.title || "").trim();
    if (!title) {
      return res.status(400).json({ error: "Title is required" });
    }
    const task = await taskService.create({ title });
    return res.status(201).json(task);
  } catch (error) {
    next(error);
  }
});

Status codes and errors

Use 200 for a successful read/update, 201 for creation, 204 for success with no body, 400 for invalid input, 401 for missing/invalid authentication, 403 for insufficient permission, 404 for missing resources, 409 for conflicts and 500 for unexpected server failures. Do not leak stack traces or secrets to clients.

Node.js execution model

Node.js runs JavaScript outside the browser and uses an event-driven, non-blocking I/O model. It is effective for many concurrent network operations, but CPU-heavy synchronous work can block the event loop. Use streams for large data and background workers or queues for long-running jobs.

Practice task: Build a CRUD API for tasks. Include validation, consistent error responses, pagination, and tests for success, invalid input, missing records and server errors.
Check your understanding

Question: What is the difference between 401 and 403?

Answer: 401 means authentication is missing or invalid; 403 means the identity is known but does not have permission.

Why: Authentication answers who you are; authorization answers what you may do.

Interview practice

Question: How would you structure a small Node API?

Strong answer should mention: Separate route/controller, validation, service/business logic and data access; centralize error handling; configure environment variables; test behavior and secure inputs.
